# 多 Agent 使用与验收

## 配置

1. 执行alembic upgrade head，应用0002迁移；旧任务仍可查询，只有新执行的分析产生AgentRun。
2. 配置MODEL_BASE_URL、MODEL_NAME和MODEL_API_KEY。可为四角色分别设置MODEL_CONDUCTOR、MODEL_ANALYSIS、MODEL_KNOWLEDGE、MODEL_REPORT，不填则继承MODEL_NAME。
3. 模型须支持OpenAI-compatible chat/completions与JSON对象输出。不要求供应商原生function calling；工具协议由Decision对象实现，服务器负责授权与分发。
4. 每个Agent有独立消息历史；共享模型并不共享业务上下文，也没有把多个Agent拆成多个公网服务。

## 真实业务操作

- 管理员在数据资产导入订单，固定表头与UTF-8编码。整批数据校验成功才入库。
- 在业务规则导入真实退款政策、渠道规范或案例，每份最多6000字符，避免一次给模型塞入不可控的大文件。
- 分析师发起任务，选择数据集、两个时间窗口与规则范围。勾选“必须具备业务规则证据”后，检索失败/无证据会阻止报告进入待审核。
- 任务创建后返回queued，Worker执行。任务详情每4秒轮询运行状态，展示四Agent目标、模型调用、Token usage与工具事件。
- 无效模型输出、非法工具、次数超限、关键分支故障都明确失败；失败不会生成模拟报告。
- 报告Agent综合服务端计算结果与已校验原文，选择关注组与排查建议。算法不宣称因果证明。
- 审核人检查报告hash绑定的内容，不能审核自己发起的报告。批准后后台实际写站内通知；驳回不发布。

## 可复现自动化验证

tests/test_multi_agent.py覆盖四角色、独立上下文、并发屏障、实际工具调用、轨迹持久化、越权拒绝、关键/可选分支、循环预算、引用范围及用户政策不可放宽。模型使用显式测试替身，数据导入、数据库查询、图执行、审批和发布使用真实应用代码。

这些测试证明软件契约与工程行为，不证明真实LLM一定理解需求或达到某个准确率。CI另外在PostgreSQL执行，不使用SQLite替代锁语义验证。

## 最终真实模型闭环验收

使用scripts.acceptance，提供本人获准使用的订单CSV与规则文档、管理员/分析师/审核人三个真实账号，以及明确时间窗口。口令交互输入或本地环境变量配置，不作为命令行参数，不写进报告。

脚本需要--allow-write，实际调用模型并写入业务数据；等待四Agent全部成功，报告必须含规则引用；随后展示报告并要求审核人输入APPROVE，才执行发布。最后核对唯一通知和report_hash，生成不含口令/令牌/订单明细的验收JSON。

本地闭环采用真实 DeepSeek，已验证四角色执行、规则引用、指标计算、独立审核和站内发布。机器可读记录见 docs/local-acceptance.json，浏览器过程图直接展示在仓库首页。本地 SQLite 验收与 PostgreSQL 的 CI 集成测试分别记录，公网后端部署仍独立验收。

DeepSeek 可设置 MODEL_THINKING=disabled，将预算用于结构化决策。协议明确每轮只允许一个 JSON 决策；格式纠正在原有四轮调用预算内执行，仍须通过工具授权与业务引用校验。不能将多个 JSON 中的第一段直接当作有效结果。
